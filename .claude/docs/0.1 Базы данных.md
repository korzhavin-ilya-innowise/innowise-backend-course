## **Типы баз данных**

База данных — организованный набор данных. СУБД — программа, которая хранит их, выполняет запросы, проверяет ограничения и разделяет доступ между клиентами. PostgreSQL — СУБД, а `myapp` внутри неё — база данных.

|Тип|Примеры|Когда подходит|
|---|---|---|
|Реляционные: таблицы, схема, связи по ключам, SQL|PostgreSQL, MySQL, SQLite|связанные бизнес-данные с транзакциями: пользователи, роли, история операций|
|Документные: JSON-подобные документы|MongoDB|объект, который читается целиком, без сложных связей|
|Ключ-значение|Redis, Memcached|кеш, счётчики rate limit, данные с TTL|
|Поисковые|Elasticsearch|полнотекстовый поиск. Источник истины остаётся в основной БД|
|Графовые|Neo4j|связи на много уровней: рекомендации, маршруты|

OLTP — много коротких операций с отдельными строками (вход, заказ). OLAP — редкие тяжёлые агрегаты по большим объёмам. PostgreSQL рассчитан на OLTP.

Реляционная БД — выбор по умолчанию для бизнес-данных. Другие типы подключают под задачу, с которой реляционная справляется плохо. В PostgreSQL часть таких задач закрывается расширениями: `jsonb`, полнотекстовый поиск, PostGIS, pgvector.

## **Реляционная модель**

Данные хранятся в таблицах. Строка описывает один объект, столбец — одно свойство фиксированного типа. Порядок строк не определён: без `ORDER BY` СУБД вправе вернуть их в любом порядке.

|Данные|Тип PostgreSQL|Почему|
|---|---|---|
|идентификатор|`uuid` или `bigint GENERATED ALWAYS AS IDENTITY`|`uuid` можно создать до вставки и он не раскрывает число записей|
|строка|`text`|`varchar(n)` такой же по скорости и только ограничивает длину|
|деньги|`numeric(12, 2)`|`real` и `double precision` дают ошибки округления|
|момент времени|`timestamptz`|хранится в UTC. `timestamp` без зоны не знает часовой пояс|
|документ|`jsonb`|для данных без постоянной структуры. Поля для фильтров и связей — отдельные столбцы|

`NULL` означает «значение неизвестно». Сравнение с `NULL` даёт `NULL`, поэтому проверка пишется как `IS NULL`, а не `= NULL`.

## **Ключи, ограничения и связи**

- **Первичный ключ** (`PRIMARY KEY`) однозначно определяет строку, уникален и не бывает `NULL`.
- **Естественный ключ** имеет смысл вне системы (`email`), но может меняться. Поэтому первичным делают суррогатный `id`, а для `email` создают `UNIQUE`.
- **Составной ключ** состоит из нескольких столбцов, например `(user_id, role_id)`.
- **Внешний ключ** (`FOREIGN KEY`) ссылается на первичный или уникальный ключ другой таблицы. СУБД не сохранит ссылку на несуществующую строку.

Ограничения проверяет сама СУБД при каждой записи, поэтому их не обойти ни параллельными запросами, ни другим клиентом.

|Ограничение|Что гарантирует|
|---|---|
|`NOT NULL`|значение обязательно|
|`UNIQUE`|значение не повторяется. `SELECT` перед `INSERT` без него не защищает от гонки|
|`CHECK`|значение удовлетворяет условию, например `status IN ('active', 'blocked')`|
|`FOREIGN KEY`|ссылка указывает на существующую строку|

При удалении родителя: `RESTRICT` запрещает удаление, пока есть ссылки; `CASCADE` удаляет зависимые строки; `SET NULL` обнуляет ссылку. Каскад подходит для частей, которые не существуют без родителя (попытка подтверждения email). Запрет — для независимых сущностей (роль, которую нельзя удалить, пока она назначена).

|Связь|Как реализуется|Пример|
|---|---|---|
|один к одному|внешний ключ с `UNIQUE`|`user_settings.user_id`|
|один ко многим|внешний ключ на стороне «многих»|`transformations.user_id`|
|многие ко многим|таблица-связка с двумя внешними ключами|`user_roles(user_id, role_id)`|

```
erDiagram
  users ||--o{ user_roles : "имеет"
  roles ||--o{ user_roles : "назначена"
  users ||..o{ transformations : "запускает"
  users {

    text status

  }
```

Концы линии — кратность: `||` ровно один, `|o` ноль или один, `}o` ноль или много. Сплошная линия (`--`) — внешний ключ входит в первичный ключ дочерней таблицы. Пунктир (`..`) — у дочерней таблицы свой `id`.

## **SQL**

|Группа|Команды|Назначение|
|---|---|---|
|DDL|`CREATE`, `ALTER`, `DROP`|структура: таблицы, индексы, ограничения|
|DML|`SELECT`, `INSERT`, `UPDATE`, `DELETE`|данные|
|TCL|`BEGIN`, `COMMIT`, `ROLLBACK`|транзакции|

```
CREATE TABLE users (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email      text NOT NULL UNIQUE,
  status     text NOT NULL CHECK (status IN ('pending', 'active', 'blocked', 'deleting', 'deleted')),
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE user_roles (
  user_id uuid REFERENCES users (id) ON DELETE CASCADE,
  role_id uuid REFERENCES roles (id) ON DELETE RESTRICT,
  PRIMARY KEY (user_id, role_id)
);

SELECT r.name, count(*) AS users_count
FROM roles r
JOIN user_roles ur ON ur.role_id = r.id
JOIN users u ON u.id = ur.user_id
WHERE u.status = 'active'
GROUP BY r.name
HAVING count(*) &gt;= 2
ORDER BY users_count DESC;

```

Логический порядок выполнения: `FROM` / `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. Поэтому `WHERE` не видит агрегаты, а `HAVING` фильтрует уже группы.

|JOIN|Результат|
|---|---|
|`INNER JOIN`|только строки с парой в обеих таблицах|
|`LEFT JOIN`|все строки левой таблицы; без пары столбцы правой равны `NULL`|
|`FULL JOIN`|все строки обеих таблиц|

Пользователей без ролей находят так: `LEFT JOIN user_roles` и `WHERE user_roles.user_id IS NULL`.

## Нормальные формы

Нормализация — это просто набор правил, как разложить данные по таблицам, чтобы при изменениях ничего не сломалось (например, чтобы при смене фамилии клиента не пришлось обновлять 100 строк в разных местах).

Во фронтенде мы привыкли к удобным вложенным JSON-объектам. Классические реляционные базы данных (SQL) работают иначе: они любят плоские таблицы и связи по ID.

На практике в бэкенде почти всегда хватает первых трех нормальных форм. Разберем их по шагам на примере интернет-магазина.

### Нулевая форма (Полный хаос)

У нас есть сырая таблица заказов. Всё свалено в кучу, как в Excel-файле.

|ID Заказа|Клиент|Товары|Менеджер|Телефон Менеджера|
|---|---|---|---|---|
|1|Иван|Ноутбук, Мышь|Петр|555-123|
|2|Анна|Клавиатура|Петр|555-123|

**Проблема:** В колонке «Товары» лежит список. Мы не можем нормально посчитать, сколько мышек купили, или сделать поиск по одному товару.

### 1NF: Правило одной ячейки (Никаких массивов)

В одной ячейке таблицы может лежать **только одно значение**. Никаких списков через запятую.

- ❌ **Плохо:** Вася купил `[Ноутбук, Мышку]`. (Как потом посчитать все проданные мышки?)
- ✅ **Хорошо:** Две строки. Вася купил `Ноутбук`. Вася купил `Мышку`.

### 2NF: Правило «Целого ключа»

Возникает только в таблицах, где главный ключ — это составная связка из двух и более колонок, и без него 2NF вообще не имеет смысла.

- Описание: Каждая обычная колонка должна зависеть от всей связки ключей целиком, а не от одной её половинки.
- ❌ Плохо: Таблица «Успеваемость». Главный ключ — связка [Студент + Предмет]. Дополнительные колонки: `Оценка` и `Имя преподавателя`.
    Здесь `Оценка` зависит от обоих ключей (Вася по физике получил 5). А вот `Имя преподавателя` зависит только от Предмета (Физику всегда ведет Петров, Вася тут ни при чем). Колонка подчиняется только половине ключа — это нарушение 2NF.
- ✅ Хорошо: Разделяем на две независимые темы.
    Таблица оценок: [Студент + Предмет] -> `Оценка`.
    Таблица предметов: [Предмет] -> `Имя преподавателя`.

Иногда в таблице нет единой колонки `id`. Чтобы сделать строку уникальной, базе приходится брать **две колонки вместе**.

Представь таблицу **«Корзина покупок»**:

- Пользователь (Вася, id=1) положил в корзину Ноутбук (id=99).
- Пользователь (Вася, id=1) положил Мышку (id=50).
- Пользователь (Петя, id=2) положил Ноутбук (id=99).

|user_id|product_id|количество|
|---|---|---|
|1|99|1 шт|
|1|50|2 шт|
|2|99|1 шт|

Может ли колонка `user_id` быть здесь Главным ключом? Нет, Вася (1) повторяется дважды. Может ли `product_id` быть ключом? Нет, Ноутбук (99) повторяется дважды.

Чтобы уникально опознать конкретную строку, мы назначаем Главным ключом **комбинацию двух колонок**: `[user_id + product_id]`. Только вместе они образуют уникальный адрес строки.

И вот теперь смотрим на 2NF:

Представь, что кто-то добавил в эту же таблицу «Корзина покупок» колонку `цена_товара`.

|[user_id + product_id] (Ключ из 2 колонок)|количество|цена_товара|
|---|---|---|
|[1 + 99]|1 шт|$1000|

Смотрим на обычные колонки:

1. `количество` — зависит от обеих колонок ключа. (Сколько штук _этого_ товара взял _этот_ юзер). Здесь всё отлично.
2. `цена_товара` — а вот цена зависит **только от `product_id`**. Цене абсолютно плевать, какой `user_id` ее покупает, она не зависит от Васи.

Вот это и есть нарушение 2NF. Колонка `цена_товара` подчиняется не всему сложному ключу `[user_id + product_id]`, а только одному конкретному куску этой комбинации (`product_id`).

**Как сделать хорошо (по 2NF):** Убрать цену из корзины. Оставить в корзине только то, что касается самой покупки, а цену перенести в отдельную таблицу `Товары`, где `product_id` будет единственным и полноправным Главным ключом.

### 3NF: Правило посредника (Никаких «друзей друга»)

Главный ключ — это ровно одна колонка.

Обычные колонки не должны зависеть от других обычных колонок. Никаких цепочек и «друзей друга». Все должны подчиняться только Главному ключу.

Представь таблицу **«Доставка заказов»**. Главный ключ — `order_id` (номер заказа).

- ❌ **Плохо (Нарушение 3NF):**


|order_id (Главный ключ)|адрес_доставки|имя_курьера|телефон_курьера|
|---|---|---|---|
|1|ул. Ленина, 5|Олег|8-999-111|
|2|ул. Мира, 10|Олег|8-999-111|

Смотрим, кто от кого зависит:

1. `адрес_доставки` зависит от заказа. Всё верно.

2. `имя_курьера` зависит от заказа (мы назначили Олега на этот заказ). Всё окей.

3. А вот `телефон_курьера` зависит от **Олега**, а не от заказа!

Получилась цепочка (паровозик): `order_id` -> `имя_курьера` -> `телефон_курьера`. Телефон «прилип» к курьеру, который сам является обычной колонкой. Это и есть нарушение третьей формы. Если Олег поменяет сим-карту, нам придется бегать по всей таблице заказов и обновлять его телефон везде.

- ✅ **Хорошо (Соблюдаем 3NF):** Разрубаем эту цепочку. Если колонка (`телефон`) зависит от кого-то другого (`курьера`), то этому «другому» пора съехать в собственную таблицу и стать там Главным ключом.

**Таблица 1: Заказы**

|order_id (Главный ключ)|адрес_доставки|courier_id|
|---|---|---|
|1|ул. Ленина, 5|99 (это Олег)|
|2|ул. Мира, 10|99|

**Таблица 2: Курьеры**

|courier_id (Главный ключ)|имя_курьера|телефон_курьера|
|---|---|---|
|99|Олег|8-999-111|

### BCNF (3.5NF): Правило «Выскочки» (Подчиненный не командует боссом)

Это редкое дополнение к 3NF. Оно нужно только тогда, когда главный ключ состоит из _нескольких_ колонок.

- Суть: Обычная колонка не имеет права втихаря диктовать значения для части главного ключа.
- ❌ Плохо: У нас сложный ключ-босс `[Студент + Предмет]`, и есть обычная колонка `Преподаватель`. Но препод Петров ведет _только_ физику. Получается, подчиненный (`Преподаватель`) решает, каким будет один из боссов (`Предмет`). Это «серый кардинал». Если все студенты отпишутся от курса, мы удалим строки и база вообще забудет, что Петров существует и ведет физику.
- ✅ Хорошо: Сделай «серого кардинала» легальным боссом. Создай таблицу, где он будет ключом: `[Преподаватель] -> Предмет`. А в таблице студентов оставь только `Студент -> Преподаватель`.

Коротко для памяти: Если колонка за кого-то решает — она должна переехать в отдельную таблицу и сама стать там главным ключом. Никакой власти без официальной должности.

Это когда мы осознанно нарушаем правила нормальных форм и дублируем данные, чтобы не делать тяжелые склейки (JOIN) при чтении (например, копируем название города прямо в таблицу юзера, чтобы не ходить за ним в справочник городов).


## Транзакции и ACID

**Пакет действий, который база выполняет как одну неделимую операцию**. Либо успешно выполняется всё, либо ничего.

**Классический пример:** Алиса переводит Бобу 100 рублей.

1. Списать 100 руб у Алисы.
2. Зачислить 100 руб Бобу.

Если после первого шага отрубится свет, деньги Алисы не должны исчезнуть в никуда. Транзакция как раз и защищает от таких ситуаций с помощью четырех правил **ACID**:

- **A (Atomicity — Атомарность): «Всё или ничего»**. Транзакцию нельзя выполнить наполовину. Либо деньги спишутся и зачислятся, либо, если на втором шаге произошла ошибка, первый шаг тоже **откатится назад**, будто его и не было.
- **C (Consistency — Согласованность): «Закон есть закон»**. Транзакция не может нарушить правила базы. Если в Postgres висит ограничение «баланс не может быть меньше нуля», а у Алисы было всего 50 рублей — база просто заблокирует всю транзакцию и ничего не изменит.
- **I (Isolation — Изолированность): «Не подглядывать»**. Пока перевод в процессе, никто другой в базе не увидит промежуточный хаос (например, что у Алисы деньги уже ушли, а Бобу еще не пришли). Другие запросы увидят базу либо строго **до** перевода, либо строго **после**.
- **D (Durability — Долговечность): «Написано пером — не вырубишь топором»**. Если Postgres ответил бэкенду «Транзакция успешна», то даже если через секунду сервер взорвется или пропадет питание, после перезагрузки жесткого диска деньги всё равно будут у Боба.

PostgreSQL — это классическая реляционная база, поэтому она гарантирует железобетонное соблюдение всех четырех букв ACID.

### Уровни изоляции

Да, уровни изоляции — это настройка той самой буквы **I (Isolation)**. Это как ползунок между «работать быстро, но с риском глюков при параллельных запросах» и «работать медленно, но абсолютно безопасно».

Когда две транзакции идут _одновременно_, могут возникать конфликты. Уровни изоляции — это ступени, которые по очереди отключают эти баги.

### 1. Read Uncommitted (Чтение незафиксированного)

- **Баг («Грязное чтение»):** Можно прочитать чужие данные, которые еще не подтверждены (commit).
- **Пример:** Алиса покупает последний iPhone. Ее транзакция стартует, количество айфонов в базе временно становится `0`. В эту же миллисекунду Боб открывает каталог, видит `0` и уходит. А у Алисы через секунду не проходит оплата, транзакция откатывается, и айфонов снова `1`. Боб упустил товар из-за «грязных» данных.
- **Фишка Postgres:** Postgres настолько строгий, что **вообще не поддерживает этот уровень**. В нем грязного чтения не бывает. По умолчанию он работает сразу на следующей ступени.

### 2. Read Committed (Чтение зафиксированного) — _По умолчанию в Postgres_

- **Как работает:** Вы читаете только те данные, которые другие транзакции уже окончательно сохранили.
- **Баг («Неповторяющееся чтение»):** Данные могут измениться _прямо во время_ вашей транзакции.
- **Пример:** Боб начинает оформлять заказ на кроссовки за 5000 руб (транзакция пошла). В этот момент админ меняет цену на 7000 руб и сохраняет. На последнем шаге оформления Боб нажимает «Оплатить», и база списывает с него 7000. Боб в шоке, потому что в начале транзакции цена была одной, а в конце — другой.

### 3. Repeatable Read (Повторяющееся чтение)

- **Как работает:** База делает для вашей транзакции «фотографию» (snapshot) данных на момент старта. Вы живете в изолированном пузыре.
- **Пример:** Боб начал транзакцию покупки за 5000. Админ поменял цену на 7000. Бобу плевать! В его «снимке» базы цена всё еще 5000, и он спокойно купит по старой цене.
- **Минус:** Если Боб и Админ попытаются _изменить_ одну и ту же строчку одновременно, база выбросит ошибку Боба и заставит бэкенд повторить транзакцию заново.

### 4. Serializable (Сериализуемость) — Идеальная строгость

- **Как работает:** База делает вид, что никаких параллельных действий нет вообще. Все транзакции выстраиваются в жесткую очередь и выполняются строго одна за другой.
- **Пример:** Два человека одновременно нажимают «Забронировать последнее место в самолете». База выполнит запрос первого, а второму сразу выдаст ошибку. Никаких накладок.
- **Минус:** Это железобетонно безопасно, но **очень медленно**.

**Короткий итог:** В 95% случаев бэкендеры оставляют дефолтный `Read Committed` и не трогают настройки базы. Если нужно защитить списание денег от параллельных запросов, уровень либо поднимают локально, либо используют ручные блокировки прямо в SQL-запросе (через `FOR UPDATE`).

## Ручные блокировки ( `FOR UPDATE`)

Cпособ сказать базе: «Я сейчас прочитаю эту строчку, чтобы принять решение, а потом буду её менять. Всем остальным — стоять и ждать!»

```sql
SELECT tickets_count FROM concerts WHERE id = 5 FOR UPDATE;
```

Вот как выглядит реальный жизненный цикл frontend + backend:

### Шаг 1: Просмотр (Никаких блокировок)

Вася и Петя заходят на страницу. Бэкенд делает обычный `SELECT` (без замков), видит 1 билет и отдает JSON. React Васи и React Пети рисуют: «Остался 1 билет». Запрос завершен, база свободна.

### Шаг 2: Ковыряние в носу (10 минут)

В базе ничего не происходит. Никаких транзакций и блокировок нет.

### Шаг 3: Гонка

Они одновременно жмут «Купить». В бэкенд прилетают два POST-запроса на покупку. Бэкенд не верит тому, что было нарисовано на клиенте. Он начинает проверять всё заново.

### Шаг 4: Момент истины (Вот тут выходит FOR UPDATE)

Для запроса Васи и запроса Пети бэкенд открывает **две новые, параллельные транзакции**. И первым же шагом внутри транзакции бэкенд идет проверять остатки билетов:

1. **Транзакция Васи:** Делает `SELECT tickets_count ... FOR UPDATE`. Получает `1` и **вешает замок**.
2. **Транзакция Пети:** Делает тот же `SELECT ... FOR UPDATE`. Натыкается на замок Васи и **зависает в ожидании** ответа от базы.
3. **Транзакция Васи:** Спокойно делает `UPDATE` (билетов теперь 0) и `COMMIT` (сохраняет). Замок снимается.
4. **Транзакция Пети:** «Отвисает». Postgres отдает ей свежие данные: `tickets_count = 0`.
5. Бэкенд Пети видит, что билетов 0. Он отменяет покупку (`ROLLBACK`) и возвращает на фронтенд Пети ошибку: `HTTP 409 Conflict`.


### Шаг 5: Реакция UI

React Пети перехватывает ошибку с бэкенда и показывает модальное окно: _«Извините, пока вы думали, билеты закончились»_.

**Итог:** `FOR UPDATE` не защищает экран. Он спасает саму математику базы в ту единственную миллисекунду, когда сервер пытается списать билет. Экран может врать, база врать не должна.

### Как устроена бронь билетов 15 мин

Секрет в том, что это **логическая блокировка** (на уровне бизнес-логики), а не физическая транзакция. Никаких зависших запросов нет — база отрабатывает за миллисекунды и идет отдыхать.

Бэкендеры просто добавляют в таблицу билетов две новые колонки: `status` (свободен, забронирован, продан) и `reserved_until` (время, когда бронь сгорит).

Механика выглядит так:

1. **Захват:** Вы нажимаете «Купить». Бэкенд делает тот самый мгновенный `SELECT ... FOR UPDATE`, чтобы никто не перехватил место в эту же миллисекунду.
2. **Смена статуса:** Бэкенд меняет `status` на `забронирован`, записывает в `reserved_until` текущее время + 15 минут, и тут же **завершает транзакцию** (COMMIT). База полностью свободна.
3. **Ожидание:** Фронтенд рисует вам таймер. Если в это время Вася зайдет на сайт, бэкенд просто не покажет ему этот билет, потому что запрос в базу выглядит как `SELECT ... WHERE status = 'свободен'`.
4. **Успех:** Если вы оплатили, бэкенд меняет статус на `продан`.

Но что, если вы передумали, закрыли вкладку и ушли спать? Билет не должен зависнуть навсегда.

Для этого на сервере крутится **фоновый процесс** (воркер или Cron-задача). Он просыпается, например, каждую минуту, и делает один простейший SQL-запрос, который как пылесос собирает весь мусор:

```sql
UPDATE tickets
SET status = 'свободен', reserved_until = NULL
WHERE status = 'забронирован' AND reserved_until < NOW();
```

Как только скрипт отрабатывает, ваша просроченная бронь сбрасывается, место снова становится зеленым на экране, и Вася может его купить.

## Индексы

Индекс находит строки без полного просмотра таблицы. Чтение ускоряется, вставка и изменение замедляются.

**Проблема:** Представь таблицу юзеров на 10 миллионов строк. Вася пытается залогиниться, и бэкенд делает запрос: `SELECT * FROM users WHERE email = 'vasya@mail.com'`. По умолчанию база работает как глупый робот (это называется _Seq Scan_ — последовательное сканирование). Она берет первую строку, проверяет email. Потом вторую. И так читает миллионы строк, пока не найдет Васю. Это чудовищно медленно.

**Решение (Индекс):** Это как алфавитный указатель в конце толстой энциклопедии. Ты даешь базе команду: `CREATE INDEX idx_users_email ON users(email);`.

База берет все емейлы, сортирует их по алфавиту и строит отдельную невидимую структуру (обычно это дерево, B-Tree). В этом дереве написано: _«vasya@mail.com лежит на жестком диске в блоке №456, строке №8»_.

Теперь при логине база не читает всю таблицу. Она за пару миллисекунд пробегается по отсортированному индексу, находит точный адрес Васи и моментально достает его данные (_Index Scan_).

### Главное правило индексов: Почему нельзя проиндексировать вообще всё?

Потому что бесплатной магии не бывает. **Индексы ускоряют чтение (SELECT), но замедляют запись (INSERT / UPDATE / DELETE).**

Если у тебя на таблице висит 10 индексов, то при регистрации нового юзера базе придется:

1. Записать строку в саму таблицу.
2. Обновить индекс по email.
3. Обновить индекс по номеру телефона.
4. Обновить индекс по дате регистрации... и так 10 раз.

Запись будет дико тормозить. Поэтому индексы вешают только на те колонки, по которым чаще всего делают `WHERE` (поиск), `JOIN` (связи) или `ORDER BY` (сортировку).

## Миграции: Git для базы данных

**Проблема:** Бэкендер Вася у себя на компе создал таблицу `users`, написал код и залил на сервер. Код запустился, попытался сохранить юзера и... сервер упал. Вася забыл зайти в базу на сервере и вручную нажать «создать таблицу».

**Решение:** Миграции. Никто не меняет структуру базы вручную. Вместо этого пишут специальные файлы со скриптами — миграции.

Каждый файл описывает одно изменение и состоит из двух частей:

1. **UP (Накатить):** например, `CREATE TABLE users;`
2. **DOWN (Откатить):** например, `DROP TABLE users;` (на случай, если релиз пошел не по плану и надо всё вернуть как было).

Эти файлы нумеруются по порядку (например, `001_create_users`, `002_add_phone_column`). База запоминает, какие номера она уже применила. Когда код едет на сервер (или когда в команду приходит новый разработчик), специальная утилита просто смотрит: _"Ага, база сейчас на шаге 1, а новых файлов уже 5"_ — и автоматически прогоняет файлы 2, 3, 4 и 5. Структура базы синхронизирована с кодом.

## Проблема N + 1: Поход в магазин за каждым яйцом

Это самая классическая ошибка производительности.

**Только ли это у ORM?** _Технически_ нет. Ты можешь и на чистом SQL написать цикл `for` в коде и внутри дергать базу. Но ORM (инструменты, превращающие таблицы в объекты кода) делают это **незаметно**, поэтому 99% случаев N+1 — это неаккуратная работа с ORM.

**Пример:** Фронтенд просит бэкенд отдать список из 10 статей и к каждой прикрепить имя автора.

- ❌ **Как делает ORM по умолчанию (Ленивая загрузка / Lazy Load):**

    1. Бэкенд говорит ORM: "Дай 10 статей". **Запрос 1:** `SELECT * FROM articles LIMIT 10;` (Это та самая цифра **1** в формуле).
    2. Дальше ORM берет массив из 10 статей и начинает его перебирать в цикле, чтобы достать авторов.
    3. Для первой статьи: **Запрос 2:** `SELECT * FROM users WHERE id = 5;`
    4. Для второй статьи: **Запрос 3:** `SELECT * FROM users WHERE id = 12;` ... и так 10 раз (Это цифра **N**).

    **Итог:** Чтобы отдать 10 статей, бэкенд сделал в базу **11 запросов** вместо одного. Если статей 100, будет 101 запрос. База ляжет от количества мелких сетевых обращений.

- ✅ **Как правильно (Жадная загрузка / Eager Load):** Бэкендер должен явно сказать ORM: _"Загрузи статьи ВМЕСТЕ с авторами"_. Тогда ORM сделает всего **два** умных запроса (или один через `JOIN`):

    1. `SELECT * FROM articles LIMIT 10;` (собрал статьи, запомнил их `author_id`: 5, 12, 18...)
    2. `SELECT * FROM users WHERE id IN (5, 12, 18...);` (достал всех нужных авторов разом).

Всё. Вместо 101 запроса сделали 2. Сервер снова дышит.

## **Типичные ошибки**

|Что видно|Причина и исправление|
|---|---|
|Роли хранятся строкой `'admin,editor'`|нарушена 1NF, нужна таблица-связка|
|Два пользователя с одним email|уникальность проверена только `SELECT` перед `INSERT`. Нужен `UNIQUE`, конфликт превращают в **409**|
|Список замедляется по мере роста таблицы|нет индекса под фильтр и сортировку|
|`JOIN` по внешнему ключу медленный|PostgreSQL не индексирует внешний ключ автоматически|
|`0.1 + 0.2` даёт `0.30000000000000004`|деньги в `double precision`, нужен `numeric`|
|Время сдвинулось на несколько часов|использован `timestamp` без зоны, нужен `timestamptz`|
|В ответ API попал `password_hash`|`SELECT *` или вся сущность ORM|
|На страницу из 20 элементов уходит 21 запрос|N+1|
|Счётчик попыток пропускает неверный ввод|потерянное обновление, нужен атомарный `UPDATE`|
|Схема на сервере отличается от локальной|изменения вносились вручную, а не миграциями|

### Почему проверка через `SELECT` перед `INSERT` не защищает от двух пользователей с одним email?

Потому что это та самая гонка (Race Condition), которую мы обсуждали с билетами.
Представь, что хитрый пользователь случайно (или скриптом) дважды нажал кнопку «Регистрация» с почтой `admin@mail.com` в одну и ту же миллисекунду. В бэкенд полетели два параллельных запроса.

1. Запрос А делает `SELECT`. База говорит: «Почты нет, свободно».
2. Запрос Б делает `SELECT`. База говорит: «Почты нет, свободно».
3. Запрос А делает `INSERT` и сохраняет юзера.
4. Запрос Б делает `INSERT` и сохраняет второго юзера с той же почтой.

Как правильно: Никакие проверки в коде от этого не спасут. Нужно на уровне самой базы повесить на колонку ограничение UNIQUE (Уникальный индекс). Тогда база сама жестко отклонит второй `INSERT` с ошибкой конфликта, а бэкенд просто перехватит её и скажет юзеру «Такой email уже есть».

`FOR UPDATE` здесь абсолютно бессилен.
В этом кроется главная ловушка: `FOR UPDATE` умеет блокировать только уже существующие строки. Нельзя повесить амбарный замок на пустоту (фантомную запись).
Вот как это отработает при регистрации нового юзера:

1. Запрос А делает `SELECT email ... FOR UPDATE`. База ищет email, видит, что его нет, и возвращает пустой ответ. Замок вешать не на что.
2. Запрос Б делает абсолютно то же самое. Тоже получает пустой ответ, замка нет.
3. Оба запроса радостно делают `INSERT`. Снова дубль.

С билетами `FOR UPDATE` работал идеально, потому что строка с концертом уже существовала в таблице до того, как Вася и Петя начали нажимать кнопки. Мы читали существующую строку и обновляли её. При регистрации же мы создаем строку с нуля.
Поэтому для защиты от дублей при `INSERT` работает только одно правило: вешать на колонку `email` жесткое ограничение базы данных `UNIQUE`. База сама на физическом уровне зарубит вторую попытку вставки и выбросит ошибку, а бэкенд её аккуратно перехватит.

### Почему индекс `(user_id, created_at)` ускоряет историю одного пользователя, но не поиск только по дате?

Потому что составные индексы в базах данных работают строго слева направо. Лучшая аналогия — это бумажный телефонный справочник.
Представь, что справочник отсортирован сначала по Фамилии (`user_id`), а затем по Имени (`created_at`).

- Ищем историю Васи (WHERE user_id = 'Вася'): Легко! Открыли справочник на букву В, нашли всех Вась в одном месте. Индекс работает на 100%.
- Ищем конкретную покупку Васи (WHERE user_id = 'Вася' AND created_at = 'Вчера'): Легко! Нашли раздел Васи, а внутри него быстро нашли «Вчера».
- Ищем все вчерашние покупки по всему сайту (WHERE created_at = 'Вчера'): Провал. Ты ищешь людей по «Имени», игнорируя «Фамилию». Тебе придется пролистать весь справочник от корки до корки, потому что «Вчерашние покупки» размазаны тонким слоем по всем Васям, Петям и Аням. Индекс бесполезен. База включит медленное последовательное сканирование таблицы.

Правило: Составной индекс работает только если ты используешь колонки в том порядке, в котором они объявлены в индексе (с обязательным участием первой). Если нужно часто искать _только_ по дате — придется создавать отдельный индекс чисто на колонку `created_at`.

### Какие аномалии возникают в таблице `user_roles_flat(user_id, role_name, email)` и какую нормальную форму она нарушает?

Эта таблица нарушает Вторую нормальную форму (2NF).

Давай разберем почему, вспомнив наше «Правило Целого ключа».
В чем проблема?
Один пользователь может иметь несколько ролей (например, Вася — и `admin`, и `editor`). Значит, колонка `user_id` сама по себе не может быть Главным ключом — Вася будет повторяться в нескольких строках.
Главным ключом здесь становится связка [user_id + role_name].
А теперь смотрим на обычную колонку `email`. Зависит ли почта от того, что Вася — админ? Нет. Почта зависит только от user_id.
Она подчиняется только _половине_ ключа. Это классическое нарушение 2NF.

1. Аномалия обновления (Update Anomaly) — лишняя работа:
    У Васи 5 разных ролей в системе, а значит, в таблице 5 строк с его `user_id`. Если Вася поменяет почту, бэкенду придется искать и обновлять email в пяти местах. Забыли обновить одну строку — получили рассинхрон данных.
2. Аномалия удаления (Delete Anomaly) — амнезия базы:
    Вася провинился, и мы решили забрать у него его единственную роль `editor`. Мы делаем `DELETE` этой строки... и база данных навсегда забывает почту Васи. Вместе с ролью удалился и сам пользователь.
3. Аномалия вставки (Insert Anomaly) — тупик для новичков:
    На сайте зарегистрировался новый юзер Петя, но админ еще не успел назначить ему роль. Мы вообще не можем добавить Петю в базу. Так как `role_name` — это часть Главного ключа, она не может быть пустой (NULL). Нет роли — нет записи.

Как исправить:
Разрезать Франкенштейна на две таблицы:
1. `users`: [user_id] -> `email`
2.  `user_roles`: [user_id + role_name] (только связка, больше никаких данных).
