### **1. ОБЩИЕ СИСТЕМНЫЕ И ARХИТЕКТУРНЫЕ ТРЕБОВАНИЯ**

Сервис проектируется как строго изолированное монолитное HTTP REST API приложение на платформе NestJS (Node.js / TypeScript), разворачиваемое в виде независимого stateless-процесса. Архитектурная стратегия объединения модулей аутентификации, разграничения доступа, управления профилями и обработки файлов в едином монолитном контуре обусловлена необходимостью обеспечения атомарной транзакционной целостности данных, минимального уровня задержек (latency) при межмодульном взаимодействии и исключения распределенного состояния. БД PostgreSQL является единственным транзакционным источником истины; использование сторонних in-memory кешей без встроенного контроля версий категорически запрещено. Отсутствие сессионного состояния в памяти процесса (stateless-архитектура на базе криптографических JWT) и абстрагирование файлового слоя через двоякую адаптерную модель позволяют масштабировать сервис путем запуска идентичных экземпляров приложения за L7-балансировщиком нагрузки. В данной топологии единая сквозная цепочка безопасности служит базовым периметром защиты, обеспечивающим абсолютный отказ в доступе по умолчанию (default-deny), предотвращающим атаки типа Cross-Site Request Forgery (CSRF), несанкционированное чтение персональных данных и исчерпание вычислительных ресурсов приложения.

#### **Архитектурная спецификация и технологический стек**

Стек технологий и системные ограничения приложения жестко регламентированы следующими компонентами:

- **Архитектурный шаблон:** Монолитное HTTP REST API (NestJS / TypeScript).
- **Реляционная база данных:** PostgreSQL. Выступает единым хранилищем системных сущностей, учетных записей, ролей, прав доступа и истории операций.
- **Слой хранения файлов (** **StorageAdapter** **):** Двухадаптерный дизайн файлового хранилища:
    - _Локальный дисковый адаптер (_ _local-storage_ _):_ применяется исключительно в средах локальной разработки и на тестовых стендах.
    - _S3-совместимый адаптер (_ _s3-storage_ _):_ применяется в продуктовом окружении (S3-совместимое объектное хранилище).
- **Криптографическая конфигурация:** Секретные ключи приложения (`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `LOGIN_CHALLENGE_HMAC_KEY`) должны иметь длину **не менее 32 байт (256 бит)** каждый. При отсутствии любого из ключей или недостижении указанной длины процедура инициализации приложения блокируется, а индикатор готовности системы принимает значение `readiness = false` с аварийным остановкой процесса.

#### **Единая цепочка безопасности (Unified Security Chain)**

Каждый защищенный входящий HTTP-запрос обязан последовательно проходить 5-этапный конвейер проверки до передачи управления контроллеру и бизнес-обработчику:

1. **Извлечение и криптографическая валидация JWT (** **access_token** **):** Токен извлекается строго из HttpOnly-cookie `access_token`. Выполняется валидация цифровой подписи (алгоритм HS256 с ключом `JWT_ACCESS_SECRET`), проверка временных меток (`iat`, `exp`), соответствие издателя (`iss = JWT_ISSUER`), получателя (`aud = JWT_AUDIENCE`) и типа токена (`token_use = "access"`).
2. **Проверка существования и статуса субъектa:** Извлеченный из claim `sub` идентификатор пользователя (`userId`) запрашивается в PostgreSQL. Система проверяет факт существования учетной записи и атрибут `status = active`. Любые иные статусы (`pending`, `blocked`, `deleting`, `deleted`) приводят к немедленному прерыванию запроса.
3. **Защита от CSRF:** Для всех запросов, изменяющих состояние системы (`POST`, `PUT`, `PATCH`, `DELETE`), поступивших из сторонних origin (cross-origin), выполняется обязательная сверка заголовка `Origin` с белым списком разрешенных доменов и проверка наличия пользовательского заголовка `X-CSRF-Protection: 1`.
4. **Проверка прав RBAC:** Запрошенное контроллером сочетание `permission@action` сопоставляется с актуальным в памяти снимком прав пользователя (in-memory policy snapshot).
5. **Проверка владения ресурсом (Ownership Check):** При операциях над персональными ресурсами `actorUserId` сравнивается с идентификатором владельца ресурса. При расхождении проверка проходит успешно только при наличии у субъекта административного разрешения с суффиксом `*_any` (например, `users@read_any`).

#### **Стандартизация HTTP-ответов и кодов ошибок**

|HTTP-код статуса|Код ошибки (Code)|Условия возникновения и семантика|
|---|---|---|
|**400 Bad Request**|`bad_request`|Ошибка валидации DTO, неверный формат файла, несоблюдение политики паролей, превышение допустимого разрешения изображения (max 4096x4096px), либо недействительный/просроченный OTP/Magic Link токен.|
|**401 Unauthorized**|`invalid_session` / `invalid_credentials`|Отсутствие или недействительность access-токена, истечение срока сессии, неактивный статус пользователя (`pending`, `blocked`, `deleting`, `deleted`), либо неверные учетные данные при входе.|
|**403 Forbidden**|`permission_denied` / `ownership_denied` / `csrf_rejected`|Недостаточность прав RBAC, провал проверки владения ресурсом при отсутствии `*_any` прав, несоответствие или отсутствие CSRF-заголовков.|
|**404 Not Found**|`not_found`|Запрошенный ресурс, пользователь или файл не существует (возвращается строго после успешного прохождения авторизации RBAC).|
|**409 Conflict**|`conflict`|Нарушение ограничений уникальности БД (дублирование email, имени роли, назначения), наличие активной задачи удаления аккаунта или попытка снизить количество администраторов с `rbac@manage` до нуля.|
|**413 Payload Too Large**|`payload_too_large`|Превышение максимально допустимого размера тела запроса или загружаемого файла.|
|**415 Unsupported Media Type**|`unsupported_media_type`|Передача файла с MIME-типом или расширением, отсутствующим в белом списке разрешенных форматов.|
|**429 Too Many Requests**|`rate_limit_exceeded`|Превышение лимитов частоты запросов (Rate Limit), блокировка повторной отправки писем до истечения 60 секунд или исчерпание попыток ввода OTP.|
|**503 Service Unavailable**|`authorization_unavailable` / `service_unavailable`|Недоступность базы данных PostgreSQL, S3-хранилища, SMTP-сервера или сбой загрузки/обновления локального снимка политики RBAC. Маршрут блокируется.|
|**504 Gateway Timeout**|`gateway_timeout`|Превышение жесткого лимита времени выполнения операции трансформации файла (>30 секунд).|

#### **Требования к безопасности и нейтрализация угроз**

- **Принцип запрета по умолчанию (Default-Deny):** Все конечные точки API защищены по умолчанию. Доступ открывается исключительно при наличии явного декоратора `@Public()`. Любые маршруты без декоратора доступа или без объявленной пары `permission@action` блокируются на этапе старта приложения с переводом индикатора готовности в состояние `readiness = false`, либо аварийно завершают обработку кодом `503 Service Unavailable`.
- **Маскирование ошибок (Error Masking):** Ответы систем аутентификации и сбоев инфраструктуры обязаны быть нейтральными. Запрещается раскрывать факт наличия или отсутствия email в системе при входе и регистрации для предотвращения атак типа Account Enumeration.
- **Фильтрация DTO (DTO Whitelisting):** Входящие структуры данных подлежат строгой валидации. Поля, не описанные в DTO, автоматически отбрасываются (stripping) до поступления в бизнес-слой.
- **Защита от атак через полезную нагрузку (Payload Attack Protection):**
    - _XXE (XML External Entity):_ В XML-парсерах принудительно отключается загрузка внешних сущностей (external entities) и DTD-структур.
    - _Decompression Bombs:_ В процессе распаковки архивов и медиафайлов выполняется контрольное инспектирование объемов выделяемой памяти с ограничением коэффициента сжатия.
    - _SVG Script Execution:_ Растеризация SVG-изображений осуществляется в изолированном окружении с предварительным жестким удалением тегов `<script>` встроенных обработчиков событий (e.g., `onload=`) и внешних URIs.

Спроектированные архитектурные ограничения и конвейер безопасности создают базовую платформу для функционирования бизнес-модулей системы, первым из которых выступает Модуль аутентификации и идентификации.

### **2. МОДУЛЬ АУТЕНТИФИКАЦИИ И ИДЕНТИФИКАЦИИ**

Модуль аутентификации обеспечивает надежное установление личности пользователей, гарантируя баланс между высокими стандартами безопасности (stateless JWT в HttpOnly cookie, алгоритмы хеширования Argon2id/bcrypt, rate limiting, HMAC-защита секретов) и удобством пользователей (поддержка одноразовых паролей OTP и ссылок Magic Link).

#### **Спецификация регистрации (`POST /auth/register`)**

1. **Обработка входных данных:**

- `email`: обязательное удаление крайних пробелов (trim) и приведение к нижнему регистру (lowercase).
- `password`: валидация длины (минимум 8 символов), обязательное наличие хотя бы одной буквы любого алфавита и одной цифры. Вводится верхняя граница длины пароля (не более 128 символов) для предотвращения атак на исчерпание ресурсов CPU и исключения усечения bcrypt на 72-м байте.

2. **Хеширование паролей:**

- Применяется алгоритм **Argon2id** (предпочтительно) или **bcrypt** с фактором стоимости `cost &gt;= 12`. Соль генерируется автоматически для каждого пароля и встраивается в итоговую строку хеша.

3. **Режимы подтверждения email (управляются флагом** **REGISTRATION_EMAIL_CONFIRMATION_ENABLED** **):**

- _Подтверждение выключено:_ В БД транзакционно создается запись пользователя со статусом `active`. В этой же транзакции пользователю назначается роль `user` (если модуль RBAC инициализирован). Возвращается `201 Created` с DTO Safe Profile.
- _Подтверждение включено:_ В БД создается запись со статусом `pending`. Генерируется запись в таблице `registration_challenges`. Клиенту возвращается `202 Accepted` со структурой: `confirmationRequired: true`, `method: "otp" | "magic_link"`, `attemptId`, `expiresInSeconds: 600`, `resendAfterSeconds: 60`. Секретный код или токен в тело ответа **никогда не включаются**.

#### **Протоколы подтверждения Email (Email Challenge Protocols)**

- **OTP (One-Time Password):** 6-значный числовой код со сроком жизни (TTL) 10 минут. Максимальное количество попыток ввода — 5 (5-я попытка может быть успешной). Код хранится в БД исключительно в виде HMAC-SHA256 (`secret_hash`), рассчитанного с использованием `LOGIN_CHALLENGE_HMAC_KEY`. Пятый неверный ввод погашает попытку с фиксированием `consumed_reason = attempts_exhausted`.
- **Magic Link:** Токен из 32 случайных байт (в base64url-кодировании) с TTL 10 минут, передаваемый клиенту в формате `attemptId.secret`. В БД хранится HMAC-SHA256 от токена. Подтверждение выполняется **строго методом** **POST /auth/register/confirm**. Запросы `GET` по ссылкам категорически запрещены от изменения состояния системы для предотвращения сжигания одноразовых токенов сканерами почтовых серверов.
- **Повторная отправка (** **POST /auth/register/resend** **):** Ограничена лимитом — не чаще 1 раза в 60 секунд. Аннулирует предыдущий секрет (`consumed_reason = replaced`), обнуляет счетчик попыток и перезапускает 10-минутный TTL.

#### **Прямой вход (`POST /auth/login`) и подтверждение входа**

1. **Лимиты частоты (Rate Limits):**

- Для `POST /auth/login` устанавливается жесткий лимит: **не более 30 запросов в минуту с одного IP-адреса** и **не более 5 неудачных попыток входа на пару (email + IP) в течение 15 минут**.

2. **Валидация учетных данных:** Нормализация email, сравнение введенного пароля с `password_hash` из БД.
3. **Защита от timing-атак и нейтральные ошибки:** В случае отсутствия email в БД, ввода неверного пароля или неактивного статуса учетной записи (`pending`, `blocked`, `deleting`, `deleted`) система возвращает идентичный ответ `401 Unauthorized` с кодом `invalid_credentials`. Если пользователь не найден в БД, система обязана выполнить фиктивную проверку хеша (dummy password hash verification) с использованием заранее сгенерированного эталонного хеша для выравнивания времени ответа API.
4. **Двухэтапный вход (если** **LOGIN_EMAIL_CONFIRMATION_ENABLED = true** **):** Генерируется запись в `login_challenges` (`otp` или `magic_link`), отправляется письмо, возвращается `202 Accepted`. Подтверждение через `POST /auth/login/confirm` проверяет лимиты, статус пользователя, погашает челлендж и устанавливает авторизационные cookies.

#### **Таблицы челленджей и статус погашения**

Таблицы `registration_challenges` и `login_challenges` содержат обязательную колонку `consumed_reason` со строгим перечнем значений enum:

- `confirmed` — попытка успешно подтверждена;
- `replaced` — секрет аннулирован вызовом повторной отправки (resend);
- `attempts_exhausted` — исчерпан лимит 5 неверных вводов OTP;
- `user_inactive` — пользователь переведен в неактивный статус до подтверждения.

#### **Жизненный цикл токенов и управление Cookie**

|Параметр / Характеристика|Access Token (`access_token`)|Refresh Token (`refresh_token`)|
|---|---|---|
|**Срок жизни (TTL)**|15 минут|30 дней|
|**Набор claims в payload**|`sub`, `iss`, `aud`, `iat`, `exp`, `token_use: "access"`|`sub`, `iss`, `aud`, `iat`, `exp`, `token_use: "refresh"`|
|**Алгоритм и ключ подписи**|HS256 / `JWT_ACCESS_SECRET` (>= 32 байт)|HS256 / `JWT_REFRESH_SECRET` (>= 32 байт)|
|**Способ доставки**|HttpOnly Cookie|HttpOnly Cookie|
|**Атрибуты Cookie**|`HttpOnly; Secure; SameSite=Strict; Path=/`|`HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh`|

- **Семантика обновления (** **POST /auth/refresh** **):** Ограничен лимитом **30 запросов в минуту на IP**. Реализует ротацию токенов без сохранения состояния (stateless). Проверяет подпись, срок жизни refresh-токена и факт наличия пользователя в БД со статусом `active`. При успехе генерирует и устанавливает новую пару cookies (`204 No Content`).
- **Семантика выхода (** **POST /auth/logout** **):** Идемпотентно очищает обе cookie (`access_token`, `refresh_token`), возвращая клиенту заголовок `Set-Cookie` с прошедшей датой и совпадающими атрибутами `Path`/`SameSite`. Всегда возвращает `204 No Content`.

Выданные и подтвержденные токены аутентификации передают контекст идентификатора пользователя (`userId`) в Модуль разграничения доступа (RBAC) для принятия решений о полномочиях.

### **3. МОДУЛЬ РАЗГРАНИЧЕНИЯ ДОСТУПА (RBAC)**

Динамическая система разграничения доступа на основе ролей (RBAC) обеспечивает централизованное исполнение принципа наименьших привилегий. Модуль гарантирует горячую перезагрузку конфигураций прав без простоя системы (zero-downtime) и абсолютное блокирование неавторизованных действий.

#### **Схема реляционной модели данных**

Модель данных RBAC состоит из 7 обязательных таблиц со строгим обеспечением целостности внешних ключей:

- `roles`: `id` (UUID, PK), `name` (text, Unique, normalized), `description` (text, max 500 chars, null), `created_at`, `updated_at`.
- `permissions`: `id` (UUID, PK), `name` (text, Unique, e.g., `users`), `description` (text, max 500 chars, null), `created_at`, `updated_at`.
- `permission_actions`: `id` (UUID, PK), `permission_id` (UUID, FK -> `permissions.id` ON DELETE CASCADE), `name` (text, e.g., `read`, `update`). Уникальное ограничение на пару (`permission_id`, `name`).
- `grants`: `id` (UUID, PK), `role_id` (UUID, FK -> `roles.id` ON DELETE CASCADE), `permission_id` (UUID, FK -> `permissions.id` ON DELETE CASCADE), `all_actions` (boolean), `created_at`, `updated_at`. Уникальное ограничение на пару (`role_id`, `permission_id`).
- `grant_actions`: `grant_id` (UUID, FK -> `grants.id` ON DELETE CASCADE), `permission_action_id` (UUID, FK -> `permission_actions.id` ON DELETE RESTRICT). Составной первичный ключ (`grant_id`, `permission_action_id`).
- `user_roles`: `user_id` (UUID, FK -> `users.id` ON DELETE CASCADE), `role_id` (UUID, FK -> `roles.id` ON DELETE RESTRICT). Составной первичный ключ (`user_id`, `role_id`).
- `rbac_policy_state`: `id` (integer, PK, единственная строка `id=1`), `version` (bigint, монотонно возрастающий счетчик), `updated_at` (timestamptz).

#### **Локальный снимок политики и динамическая перезагрузка (Snapshot Reload)**

1. Сервис поддерживает в оперативной памяти процесса полный снимок политик доступа (роли, разрешения, действия, назначения пользователей).
2. При обработке запроса сервис сравнивает версию локального снимка с значением `rbac_policy_state.version` в PostgreSQL.
3. Если версия в БД превышает локальную, процесс задерживает выполнение, загружает новый снимок из БД, валидирует целостность графа прав и атомарно заменяет ссылку на локальный снимок.
4. В случае сбоя загрузки или невалидности снимка сервис блокирует обработку защищенных маршрутов с возвратом ошибки `503 Service Unavailable` (`authorization_unavailable`).

#### **Полный каталог разрешений и действий системы**

Состав разрешений и действий системы строго ограничен следующим перечнем:

- Разрешение `users`: действия `read`, `read_any`, `update`, `update_any`, `delete`, `delete_any`, `list`.
- Разрешение `transformations`: действия `convert`, `history`, `history_any`, `download`, `download_any`.
- Разрешение `rbac`: действие `manage`.

#### **Первичная инициализация (Bootstrap) и инвариант администратора**

- **Инициализация (Bootstrap):** Выполняется автоматически при старте приложения на пустых таблицах RBAC. Создает разрешения (`rbac`, `users`, `transformations`) и их действия. Генерирует роли `user` и `admin`. Роли `user` назначаются `users@read`, `users@update`, `users@delete`. Роли `admin` назначается `rbac@manage` и абсолютно все действия разрешений `users` и `transformations`. Пользователю с ID из конфигурации `RBAC_BOOTSTRAP_ADMIN_USER_ID` назначается роль `admin`. Все существенные активные пользователи без ролей в той же транзакции получают роль `user`.
- **Инвариант суперадминистратора:** Любая административная операция (изменение ролей, отзыв прав, удаление пользователей), проведение которой приведет к тому, что в системе останется **0 пользователей** с разрешением `rbac@manage`, обязана транзакционно отклоняться с ответом `409 Conflict`.

#### **Спецификация административного API (`/admin/rbac/*`)**

|Эндпоинт|Метод|Тело запроса / Параметры|Валидация и обработка ошибок|
|---|---|---|---|

Сконструированная система контроля доступа обеспечивает безопасность операций над сущностями пользователей, регламентируемых Модулем управления пользователями и профилями.

### **4. МОДУЛЬ УПРАВЛЕНИЯ ПОЛЬЗОВАТЕЛЯМИ И ПРОФИЛЯМИ**

Модуль управляет жизненным циклом профилей пользователей, аватарами, обеспечивает корректную обработку персональных данных и предоставляет механизмы асинхронного анонимизированного удаления учетных записей.

#### **Контракт безопасного профиля (Safe Profile Contract)**

Внешние ответы API, содержащие данные пользователя, подлежат строгой проекции на DTO `Safe Profile`, состоящее ровно из 7 полей:

1. `id` (UUID)
2. `email` (string, нормализованный)
3. `displayName` (string | null)
4. `photoUrl` (string | null) — URL конечной точки API (`/users/{userId}/photo`), **абсолютно исключая внутренний ключ S3**
5. `status` (`"pending"` | `"active"` | `"blocked"` | `"deleting"` | `"deleted"`)
6. `createdAt` (string, ISO 8601)
7. `updatedAt` (string, ISO 8601)

_Категорически запрещено включать в DTO хеши паролей, HMAC-секреты, ключи хранилища (_ _photo_key_ _), служебные версии или JWT._

#### **Операции с профилем и аватаром**

- `GET /users/{userId}`: Требует разрешение `users@read`. При несовпадении `targetUserId != actorUserId` требуется разрешение `users@read_any`. Возвращает DTO Safe Profile.
- `PATCH /users/{userId}`: Требует `users@update` (`users@update_any` при смене чужого профиля). Обновление текстовых полей (`displayName`). При изменении email запускается двухэтапный процесс подтверждения нового адреса с сохранением текущей сессии.
- `PUT /users/{userId}/photo` & `DELETE /users/{userId}/photo`: Загрузка и удаление аватара.
    - _Конвейер загрузки:_ Проверка MIME-типа изображения, удаление EXIF-метаданных, изменение размера и конвертация в формат WebP (максимум 1024x1024 px).
    - _Очистка хранилища:_ При замене или удалении аватара предыдущий файл удаляется асинхронно — запись с ключом устаревшего файла помещается в таблицу БД `storage_cleanup_jobs` для фоновой утилизации воркером, предотвращая блокировку HTTP-ответа.
- `GET /users/{userId}/photo`: Возвращает бинарный поток изображения с заголовком `Content-Type: image/webp`.

#### **Протокол асинхронного удаления аккаунта (`DELETE /users/{userId}`)**

Операция полного удаления учетной записи спроектирована по двухфазной асинхронной схеме, исключающей таймауты HTTP-соединений и гарантирующей идемпотентность исполнения.

##### **1. Фаза приема и валидации запроса (Ingestion Phase)**

- Клиент отправляет запрос `DELETE /users/{userId}` с опциональным заголовком `Idempotency-Key` (16 случайных байт в виде 32 hex-символов).
- Сервер проверяет наличие прав (`users@delete` или `users@delete_any`) и наличие уже запущенных процессов удаления.
- В рамках единой транзакции БД:
    - Статус пользователя переводится в значение `deleting`.
    - Создается задача удаления с `jobId`, равным значению `Idempotency-Key` (если ключ не передан, `jobId` генерируется сервером).
- Сервер немедленно возвращает ответ `202 Accepted` со структурой `{ "jobId": "&lt;32_hex_chars&gt;", "status": "deleting" }`.

##### **2. Фаза фонового исполнения (Background Execution Phase)**

Фоновый воркер очистки (`deletion-worker`) периодически извлекает задачи в статусе `deleting` и последовательно выполняет модульные стиратели (erasers):

- **Avatar Eraser:** Вызывает метод `delete()` у `StorageAdapter` для удаления файла аватара из S3 или локального диска.
- **Personal Data Eraser:** Анонимизирует персональные данные пользователя в таблице `users`. Поле `email` перезаписывается маской `deleted.&lt;32_hex_random&gt;@example.invalid`, поле `displayName` сбрасывается в `null`.
- **Data Purge Eraser:** Очищает все активные челленджи (`registration_challenges`, `login_challenges`), связанные токены и историю сессий.

##### **3. Финализация и гарантированная идемпотентность (Finalization Phase)**

- По завершении работы всех стирателей статус пользователя в БД транзакционно переводится в `deleted`.
- Повторные вызовы `DELETE /users/{userId}` с тем же или новым `Idempotency-Key` не создают дублирующих задач, являются идемпотентными и возвращают существующий `jobId` и текущий статус обработки.

#### **Административный список пользователей (`GET /admin/users`)**

- **Безопасная пагинация (Keyset Pagination):** Используется курсорная пагинация по составному кортежу `(created_at, id)`.
- **Защита курсора:** Передаваемый клиенту непрозрачный токен курсора шифруется/подписывается с помощью HMAC для предотвращения подмены параметров пагинации на стороне клиента.
- **Зафиксированный снимок времени (** **snapshotAt** **):** Запрос принимает или генерирует метку времени `snapshotAt`, исключающую сдвиг страниц (pagination drift) при добавлении новых пользователей во время итерации.
- **Фильтрация:** Строгий белый список фильтров (`status`, `created_after`, `created_before`, подстрочный поиск `search` по `email` и `displayName`).

Управление профилями и учетными записями дополняется функционалом обработки пользовательских данных, подробно описанным в Модуле трансформации файлов и хранилища.

### **5. МОДУЛЬ ТРАНСФОРМАЦИИ ФАЙЛОВ И ХРАНИЛИЩА**

Модуль обеспечивает потоковую трансформацию текстовых и медиафайлов, строгий контроль потребления оперативной памяти, защиту от векторов атак через загружаемый контент и временное или постоянное хранение результатов обработки.

#### **Ограничения ядра конвертации (Converter Core Engine)**

- **Потоковая обработка:** Преобразование файлов осуществляется строго через конвейер потоков (streaming processing) без полной загрузки файла в оперативную память.
- **Таймаут исполнения:** Установлен жесткий лимит времени выполнения операции в **30 секунд**. При превышении процесс прерывается и возвращается код `504 Gateway Timeout`.
- **Контроль размера:** Превышение глобального лимита размера файла на входе блокируется кодом `413 Payload Too Large`.

#### **Движок конвертации текстовых форматов (`POST /api/convert`)**

- **Требуемое разрешение:** `transformations@convert`.
- **Матрица поддерживаемых направлений:** Движок строго поддерживает **12 явных путей конвертации** между форматами CSV, JSON, XML и YAML:
    1. `CSV -&gt; JSON`
    2. `CSV -&gt; XML`
    3. `CSV -&gt; YAML`
    4. `JSON -&gt; CSV`
    5. `JSON -&gt; XML`
    6. `JSON -&gt; YAML`
    7. `XML -&gt; CSV`
    8. `XML -&gt; JSON`
    9. `XML -&gt; YAML`
    10. `YAML -&gt; CSV`
    11. `YAML -&gt; JSON`
    12. `YAML -&gt; XML`
- **Требования безопасности:**
    - _YAML:_ Безопасный парсинг с полным отключением возможности инстанцирования произвольных DTO и объектов кода.
    - _XML:_ Строгое отключение обработки внешних сущностей (anti-XXE) и DTD-структур.

#### **Движок конвертации изображений (`POST /api/images/convert`)**

- **Требуемое разрешение:** `transformations@convert`.
- **Поддерживаемые форматы:** PNG, JPEG, SVG (только в качестве входного формата для растеризации).
- **Ограничения на размеры:** Максимальное разрешение входных и выходных изображений — **4096x4096px**. При превышении предела обработка блокируется с кодом `400 Bad Request`.
- **Защита от атак:** Защита от "декомпрессионных бомб" (zip/image bombs) путем контроля размера буфера в процессе декодирования.
- **Приватность и обработка:** Автоматическое удаление всех EXIF-метаданных, возможность настройки параметров качества JPEG, принудительное уплотнение (flattening) альфа-канала прозрачности на белый фон при конвертации прозрачных изображений в непрозрачные форматы (e.g., PNG -> JPEG).

#### **Реестр форматов и история операций**

- `GET /api/convert/formats` и `GET /api/images/convert/formats`: Возвращают матрицу поддерживаемых направлений трансформации.
- `GET /api/transformations/history`: Требует разрешение `transformations@history` (или `transformations@history_any` для просмотра глобальной истории). Возвращает список прошлых операций пользователя с курсорной пагинацией по кортежу `(created_at, id)`, HMAC-подписью курсора и параметром `snapshotAt`.

#### **Сохранение в хранилище и политика удержания (Retention Policy)**

- **Флаг долговременного сохранения (** **save=true** **):** При наличии параметра `save=true` в запросе на трансформацию, обработанный файл асинхронно сохраняется в S3 или на локальный диск через `StorageAdapter` под уникальным случайным ключом.
- **Защищенное скачивание (** **GET /api/transformations/history/{itemId}/download** **):** Требует `transformations@download` (`transformations@download_any`). Отдает файл клиенту в виде бинарного потока с заголовками `Content-Type` и `Content-Disposition`.
- **Автоматическая очистка (Data Retention Policy):** Фоновый воркер `retention-worker` запускается раз в 24 часа и автоматически удаляет сохраненные артефакты трансформаций, срок хранения которых превысил **90 дней**, стирая объекты из хранилища и обновляя статусы записей в истории.

Спецификация данного Технического Задания полностью исчерпывает архитектурные, функциональные и нефункциональные требования к бэкенд-сервису и является конечным строгим руководством для этапа разработки, проведения аудита безопасности и автоматизированного тестирования.
